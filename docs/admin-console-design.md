# 图序 · admin 超级管理台设计方案

设计日期：2026-10-27（北京时间）  
状态：设计方案，待实现。本文描述拟议能力，当前版本尚未提供超级管理台。

现有账号和工作区权限见 [账号、工作区与协作权限](accounts.md)。

## 交互原型

用浏览器直接打开 [超级管理台交互原型](prototypes/admin-console.html)，无需启动项目服务，可点击查看用户管理、工作区管理、管理模式及操作记录，并体验密码重置、账号禁用、所有权转让等流程。

原型全部使用示例数据，操作只影响当前页面中的演示数据，不连接实际账号或工作区；刷新后恢复初始演示数据。可编辑的 [原型源文件](prototypes/admin-console.fragment.html) 一并保留；修改源文件后需重新导出独立预览页。

## 1. 权限模型

在全局账号层新增 `systemRole: user | super_admin`。默认 admin 为唯一超级管理员；普通账号仍通过工作区成员关系取得所有者、编辑者或查看者权限。

admin 可管理全部账号、全部工作区，并以“超级管理员”身份进入工作区，查看和编辑业务资料、成员、邀请及配置。工作区保留原来的所有者，admin 无需加入成员列表；页面持续显示“超级管理模式 · 当前工作区”。所有修改、任务及管理操作均记录真实操作者 admin。

首版不提供超级管理员任命入口。admin 的密码仍由 `APP_PASSWORD` 管理；后台禁止禁用、删除或降低该账号的系统角色。

## 2. 页面结构与入口

- admin 顶栏账号菜单新增“超级管理台”，独立地址 `/admin`，默认打开用户管理。
- 普通账号不显示入口；直接访问后台页面及接口返回无权限。
- 管理台拥有独立的导航：用户管理、工作区管理、操作记录。顶栏保留“返回我的工作台”。
- 配色、按钮、标签和表格沿用图序现有设计系统；全局管理和空间内成员管理使用明确不同的标题。
- 首版优先做好列表与详情，不放无实际业务用途的总览图表。

## 3. 用户管理

列表展示：用户名、全局名称、账号状态、所属工作区数量、创建时间；支持搜索、状态筛选和服务端分页。

| 操作 | 行为 |
| --- | --- |
| 新建账号 | 填写用户名、个人名称和初始密码；可暂不分配工作区，或由工作区详情添加成员。用户名唯一、不创建隐含工作区。 |
| 用户详情 | 查看全局资料，以及每个工作区内的角色、成员状态和当月成功生图数；点击工作区进入其管理详情。 |
| 编辑名称 | 只修改全局个人名称；工作区内称呼继续由成员设置维护。首版不改用户名。 |
| 重置密码 | 为普通有效账号设置新密码，原密码不可查看；同事务撤销该账号全部登录会话。待激活账号沿用邀请流程，已禁用账号须先显式启用。 |
| 强制下线 | 撤销全部会话，不改变账号状态、密码或成员关系；用户仍可重新登录。 |
| 全局禁用 / 启用 | 禁用阻止登录、邀请接受和所有工作区的新请求，并撤销会话及未兑现的定向邀请；启用只恢复账号状态，不恢复被撤销的邀请或被禁用的成员关系。 |

禁用确认框列明影响：全部工作区访问、登录会话、该用户拥有的工作区数量；不删除产品、图片和历史记录，不自动转让所有权。已有排队及执行中的任务保持现有行为，继续完成；如需停止，从对应工作区任务队列单独取消。其他有效成员可继续使用工作区，所有者被禁用的工作区提示 admin 处理所有权。

用户详情明确区分“账号已禁用”和“某工作区成员已禁用”。首版不提供永久删除账号，以保留资料归属和操作记录。

全局禁用针对已激活账号；待激活账号由邀请状态控制，详情提示通过工作区撤销邀请，不把待激活账号直接启用为有效账号。

## 4. 工作区管理

列表展示：名称与 ID、所有者、成员数、启用 / 归档状态、创建时间；支持名称 / ID / 所有者搜索、状态筛选和服务端分页。

工作区详情按需展示以下内容：

- **基本资料**：重命名、归档 / 恢复、转让所有权；创建时必须指定一个有效账号为所有者。
- **成员与邀请**：添加有效账号、邀请、修改角色、修改空间内称呼、禁用 / 恢复 / 移除成员及撤销邀请。
- **配置**：管理现有模型、并发和 API Key 配置；密钥只展示是否配置及脱敏标识，支持替换和清除，不返回明文。
- **用量**：按工作区、成员和北京时间自然月查询成功生图用量，保持现有计数口径。
- **进入工作区**：在当前 admin 会话中打开业务界面，显示“超级管理模式”及“返回管理台”；具备该空间的查看、编辑、生成和管理能力。

归档规则继续沿用现有规则：存在排队、执行中或中断未结束任务时先处理任务，再归档。归档后，admin 仍能查看管理详情和只读业务资料；恢复后才可编辑资料或发起任务。

转让要求目标为本工作区已加入的有效成员；在单个事务内完成降级、升级及审计，始终保留唯一所有者。admin 不会因进入工作区自动成为所有者。首版不提供永久删除工作区。

## 5. 超级管理模式

从“工作区管理 → 进入工作区”进入。上下文示例：

> 超级管理模式 · 电商主图组 · 操作者：admin　[返回管理台]

普通工作台保留“我的工作区”；管理台列出“全部工作区”。当前标签的 URL 与请求绑定目标工作区；进入其他工作区前按现有流程保存草稿，多标签可以分别打开不同空间。

跨空间操作仍受真实工作区范围、输入校验、资产归属、并发限制、归档状态和队列规则约束。超级权限解决访问与管理资格，不绕过这些业务规则。

由 admin 发起或重试的任务记录 admin 为操作者，使用目标工作区的模型和密钥，不冒用原所有者。admin 不占普通成员的月额度；成功结果继续计入该空间总用量，单独显示“管理员操作”来源。原成员发起的既有任务不改变归属。

## 6. 操作记录

首版记录：新建账号、修改个人名称、密码重置、强制下线、全局启停；工作区创建、重命名、归档、恢复和所有权转让；管理员修改成员、邀请、密钥及配置；进入管理模式。

每条记录包含北京时间、真实操作者 ID、操作名称、目标账号 / 工作区、结果和请求 ID。修改保存经过字段白名单过滤的前后差异；密码、密钥、Cookie、邀请令牌均不进入日志。工作区内产品和素材修改沿用现有活动记录，并正确标识 admin；任务记录保留真实发起人和重试者。

管理写入与审计在同一事务内成功；失败结果按脱敏后的错误码单独记录。支持按目标、操作类型和日期筛选，采用服务端分页。

## 7. 现有代码的落地点

1. **身份**：追加数据库迁移，为 `accounts` 增加 `system_role`；仅将固定默认账号 `OWNER_ID` 初始化为 `super_admin`。`UserIdentity` 暴露 `systemRole`，登录及每次会话解析都从数据库读取。
2. **后台路由**：新增 `admin.ts`、`admin-routes.ts`；`/api/admin/*` 在登录身份验证后、工作区成员解析前验证系统角色。不能只标记 `accountOnly` 就放行；所有后台读写均强制系统权限，写事务内复核。
3. **统一鉴权**：扩展 `workspace-access.ts`，将成员模式与管理模式变成明确的访问上下文；保留真实成员角色，管理权限从服务端系统角色推导。普通成员仍走现有规则，禁止把 admin 伪装成 owner 或为所有工作区批量插入成员行。
4. **上下文与前端**：更新 `authentication.ts`、`AuthRouter.tsx` 和服务端请求上下文；管理台不依赖有效工作区。新增 `src/ui/admin/`、对应服务和状态层；旧 `can(role, permission)` 调用逐步接入新的能力判断，管理模式明确标注身份。
5. **全部访问通道**：统一覆盖普通 HTTP、事务内写入、原生图片 / 下载、SSE 连接及定期复查、会话刷新和工作区切换；不得只在列表或页面路由放开权限。前端模式参数仅表达意图，不能授予权限。
6. **任务与用量**：修改 `assertImageQuota` 及 `recordImageSuccess` 对有效成员关系的硬依赖，允许真实 admin 操作者完成管理任务，并继续原子、幂等地记账；工作区总计需包含“管理员操作”，成员列表不增加隐含管理员。
7. **全局状态**：禁用账号在同一事务更新全局状态、撤销会话与定向邀请；重置密码和强制下线分别维护自身语义。工作区成员状态及所有权不被间接改写。
8. **审计**：增加 `admin_audit_logs`；采用独立字段及服务，避免把全局管理操作塞入某个默认空间。追加迁移，不修改历史 SQL。

推荐接口分组：

```text
GET  /api/admin/accounts
POST /api/admin/accounts
GET  /api/admin/accounts/:id
PATCH /api/admin/accounts/:id
POST /api/admin/accounts/:id/reset-password
POST /api/admin/accounts/:id/revoke-sessions
POST /api/admin/accounts/:id/disable
POST /api/admin/accounts/:id/enable

GET  /api/admin/workspaces
POST /api/admin/workspaces
GET  /api/admin/workspaces/:id
PATCH /api/admin/workspaces/:id
POST /api/admin/workspaces/:id/archive
POST /api/admin/workspaces/:id/restore
POST /api/admin/workspaces/:id/transfer-owner
POST /api/admin/workspaces/:id/access

GET  /api/admin/audit-logs
```

成员、邀请、配置和业务接口复用现有模块；其服务与事务内部必须接受经过验证的管理上下文。后台端点统一做输入白名单、分页上限与服务端鉴权，既有同源校验和会话保护继续生效。

## 8. 实施与验收

实现分为三个可验证步骤：先打通系统角色与统一鉴权，再完成用户 / 工作区列表及管理操作，最后接入跨空间工作台、管理员任务计量和操作记录。

必须验证：普通账号无法访问或伪造后台权限；admin 不作为成员也能管理空间；工作区范围不串用；归档规则生效；全局禁用与成员禁用互不混淆；修改密码及下线立即撤销旧会话；所有者唯一；admin 不可自禁用；HTTP / SSE / 图片 / 下载鉴权一致；管理员生成任务正确归属与幂等记账；审计无敏感值。迁移后原账号、会话、成员、密钥与工作区资料可继续使用。

落地代码后执行仓库要求的 `npm test`、`npm run build` 及相关浏览器回归。本次设计未修改应用代码、数据库或现有权限。
